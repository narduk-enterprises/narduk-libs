## 1. Goal

One canonical Apple MapKit JS library, built and published from narduk-libs,
that carries the best implementation of every capability the estate has written
more than once, with every consumer on an immutable published
`@narduk-enterprises/*` release and every earlier iteration frozen, its missing
features migrated, and listed for fast-track deletion. "One library" means one
workspace home and one release train; it does not by itself mean one npm package
— that is decision D1 in §12.

Done when:

- `packages/modules/narduk-mapkit` and `packages/modules/narduk-mapkit-nuxt` are
  the canonical reusable MapKit JS sources for scheduled W2/W3 consumers (two
  packages, D1): no vendored MapKit library, MapKit `file:` tarball or git-ref
  dependency, or duplicate token route, loader or `AppMapKit` in those
  consumers. Product-owned rendering stays (§6); frozen, hold, personal and
  unranked W4 repositories remain recorded exceptions.
- Every scheduled consumer pins a published `@narduk-enterprises/narduk-mapkit*`
  version from the consolidation release (core-only consumers install only
  core), and `foundation:check` item 3 stays green on each applicable app.
- The superseded libraries are frozen (§9): no agent has updated one since
  2026-09-14; every capability they carry that narduk-libs lacked has shipped
  from narduk-libs (§6); the fast-track deletion note (§9.3) and its company-hq
  issue hold the deletion preconditions; `company-hq#159` is closed.
- Each capability absorbed from an app has a test in the library and the
  app-local copy is deleted in its consumer adoption PR after the library
  release is available. Frozen source repositories remain untouched (§9).

## 3. Governance already decided — not re-litigated here

- **Logan's direction, 2026-09-14 (primary in-session authorization).** Logan:
  "For this cleanup, we dont have to retire the libs that you identify as

  company-hq#741. The "old repos" are the repositories whose only content is a
  superseded MapKit library (§9.3); a repository that also holds live product
  code is frozen for its MapKit copy only.

  `docs/runbooks/RETIREMENT-CHECKLIST.md` runs confirm-then-retire, never

  exception for the repositories §9.3 names, so a deletion waits for a dated
  `DECISIONS.md` entry, confirmed by Logan, that names the repository (human

  `@narduk-enterprises` (company-hq D-FOUND-2 (6), 2026-07-25).
- **Home.** narduk-mapkit (both packages) folds into narduk-libs `modules/`;
  `company-hq#159` is the fold issue; the decommission ledger's "never

### 5.7 Live-risk findings that should not wait for the plan

1. **Tokens minted without the `mapkit_js` scope.** Core 2.0.2 / adapter 2.0.4
   added the scope Apple requires at its JavaScript bootstrap endpoint for
   dynamically signed tokens. Still on pre-fix code: earthdata-viewer (vendored
   2.0.0 dist; dynamic signing is the configured production path), hydrogen,
   harvest-tracker, my-farm, narduk-family-location and vtraceroute (exact 2.0.0
   pins). Whether each production deployment signs dynamically or serves a
   static token cannot be read without secret values and was not read;
   narduk-family-location's dev script names dynamic signing. The remedy is the
   same either way: the independently gated patch bump described before the W2
   table, which need not wait for W1.
2. **Token routes with no allowlist and no rate limit** in austin-texas-net and
   float-forecast (§5.3). The layer's own route has both; the app overrides
   dropped them. Adopting the adapter route (W2 for float-forecast, W3 for
   Austin) restores the origin allowlist only when `MAPKIT_ALLOWED_ORIGINS` is
   set, because the core admits every origin when the list is empty
   (`server/shared-config.ts:68-72`); rate limiting returns through the 3.0.0
   enforced policy (§6 #20), switched on in the same adoption PR. If a wave
   slips, deleting the app's override makes the layer's own route (allowlist +
   60 req/min policy) serve again; that is a consumer edit, not an update to the
   frozen layer.
3. **farm-analytics on the retired `@narduk-geo` scope** (narduk-libs#140): not
   live risk (no deployment), but it fails foundation:check item 3 and must move
   scopes, not just versions.

## 6. Best-of adjudication — what the consolidated library absorbs

Rule used: Logan's 2026-09-14 direction (§3). Every capability that a superseded
library or copy carries and narduk-libs lacks migrates: the template layer at
every published version, Austin's fork and the vendored copies. So do the gaps
this plan first deferred: time-cursor playback, client-side geocoding and
single-image placement. Beyond those, the library absorbs a capability when two
or more apps implement it, or one app implements it and the adapter
re-implements it internally, **and** it is not product-specific.
Product-specific stays put: tile baking (D1), the Texas polygon and its tuning
(ledger rows 337, 540), engines and fallback renderers, and each app's own
geolocation UX. New APIs are additive and existing public names remain
source-compatible except for the explicitly approved major-release behavior
changes: **MapKit JS v6 becomes the default and crossfades progress and complete
correctly (#1)**. D3 records Logan's aggressive-move direction and this
interpretation. New token policies remain opt-in and off. The 3.0.0 migration
guide must document both changes, v6 API differences and explicit v5 selection
for a bounded compatibility fallback; v5 is not the adoption target. The clock
and fallback proof below applies independently of the SDK version.

## 7. Target architecture

D1–D4 are recorded in §12. Both existing packages release together at 3.0.0 with
MapKit JS v6 as the default. No React wrapper, dependency, peer dependency or
React export is introduced. Existing React apps can consume the plain core.

- **Two packages, names unchanged.** `@narduk-enterprises/narduk-mapkit`
  (framework-agnostic: `client`, `geometry`, `playback`, `server`, `worker`,
  `node`, `token`, `apple-maps`) and `@narduk-enterprises/narduk-mapkit-nuxt`
  (module, `AppMapKit`, `AppMapKitCallout`, composables, token route, and the
  new `./types` and `./markers` exports). my-farm (React), the hydrogen and
  my-farm Workers, earthdata-viewer and gonogo's engine consume the core without
  Vue or Nuxt. A single package would need optional peer dependencies and
  isolated exports to retain that boundary; a subpath alone does not prove it.
  D-NAME-1 governs repository renames and explicitly excludes package names;
  D-WEBFOUND-2 Q7 parks those renames until folds land. Twelve repositories
  import these package names today: the eleven registry consumers in §2 I7 plus
  earthdata-viewer's vendored copy.
- **One release train.** `.changeset/config.json` gets
  `"fixed": [["@narduk-enterprises/narduk-mapkit", "@narduk-enterprises/narduk-mapkit-nuxt"]]`
  (today both arrays are empty), so both packages always publish at the same
  version and "pinned from the same release" is checkable by equality. Cost: an
  adapter-only change also publishes a no-op core patch. First fixed release:
  **3.0.0** for both (major: v6 default and clock behavior repair). The D2
  answer chose the fixed group with the then-proposed 2.1.0; D3's aggressive
  major move supersedes only that version number, not fixed versioning.
- **Generator stays in lock-step by gate.** `versions:check`
  (`scripts/sync-generator-package-versions.mjs --check`) already fails when
  `create-narduk-app`'s manifest (`manifest.ts:6-7`) drifts from workspace
  versions, and `foundation:check` item 3 keeps rejecting `@narduk-geo`.
- **Docs.** The adapter README owns the consumer contract (props, slots, events,
  exposed methods, module options, token route, rate limiting, script URL
  selection, unavailable slot, markers); the core README owns the primitives.
  `docs/centralization-plan.md` gets a banner pointing here and is otherwise
  left as history. `package.json` `homepage`/`bugs` move to narduk-libs.
- **Frozen predecessors stay out of the build.** Nothing in this architecture
  depends on a §9.1 item. No wave publishes, patches or vendors from one; W2 and
  W3 remove each consumer's dependency on one, and behaviour only the layer had
  arrives as opt-in options on the two packages (§6 #20–#22).
- **Secrets contract unchanged.** `APPLE_TEAM_ID`, `APPLE_KEY_ID`,
  `APPLE_PRIVATE_KEY`, `MAPKIT_ALLOWED_ORIGINS` (and `NUXT_` forms) from the
  shared `apple/prd/mapkit-signing` persona. The dead `MAPKIT_SERVER_API_KEY` /
  `NUXT_MAPKIT_SERVER_API_KEY` catalog entries
  (`narduk-platform/src/env-catalog.ts:171,766-792`) are marked deprecated in W1
  and removed in a later narduk-platform release.

### 9.2 What frozen means

Frozen means no agent commit, branch, pull request, tag, release, publish,
version bump, dependency or workflow update, issue comment or close, README
edit, archive, or registry deprecation on a §9.1 item, and no copying or
vendoring from one into a live repository. A bug found in a frozen library is
fixed in narduk-libs (AGENTS.md § Library-first fixes), and its consumer moves
to the fixed release. A consumer removing its own vendored copy or fork as it
adopts the registry pair is a migration step, not an update to the frozen
library, and stays in W2 and W3. A production incident that seems to need a
change in a frozen library goes to Logan. Nothing enforces the freeze
(enforcement: none yet); archiving the standalone repository would, and that is
Logan's call.
